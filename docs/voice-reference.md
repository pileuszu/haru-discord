# 한국어 참조 목소리

현재 개인 Discord 테스트에는 KSS(Korean Single Speaker Speech Dataset)의 같은 전문 여성 성우 녹음을 참조로 사용한다. 방송 아나운서의 녹음을 수집한 자료가 아니라, 한국어 음성 합성을 위해 공개된 데이터다. 기존 macOS Yuna 합성 참조 파일은 덮어쓰지 않고 보존한다.

## 출처와 이용 조건

- 원저작자: Kyubyong Park, *KSS Dataset: Korean Single speaker Speech Dataset*, 2018.
- 원 배포처: [Kaggle KSS](https://www.kaggle.com/bryanpark/korean-single-speaker-speech-dataset/kernels).
- 개별 음성 다운로드 미러: [Bingsu/KSS_Dataset](https://huggingface.co/datasets/Bingsu/KSS_Dataset).
- 데이터 라이선스: [CC BY-NC-SA 4.0](https://creativecommons.org/licenses/by-nc-sa/4.0/). 비영리로 사용하고 출처·라이선스·변경 내용을 표시한다. 수정한 참조 음성을 배포할 때는 같은 라이선스를 적용한다. 저장소 코드의 라이선스로 음성 데이터의 조건을 대체하지 않는다.
- 배포자는 한국어 TTS용 데이터이며 전문 여성 성우의 녹음이라고 설명한다. 이를 성우 개인의 보증이나 모든 상업적 음성 복제에 대한 허락으로 해석하지 않는다.

참조 FLAC과 원본 클립은 Git에서 제외된 `.runtime/voices/kss/`에 보관한다. 함께 생성한 manifest와 출처 문서에는 원본 행 번호·전사문·해시·변환 내용을 기록한다. 참조 음성을 다른 사람에게 전달할 때도 출처 문서를 함께 전달한다.

## 준비와 적용

```bash
cd ~/repos/haru-discord
.venv/bin/python scripts/prepare_kss_voice.py
```

같은 화자의 서로 다른 완결된 문장을 짧은 간격으로 이어 약 30초 및 3분에 가까운 파일을 만든다. 24 kHz 모노 PCM16 FLAC으로 변환하며, 재생 속도·피치 변경이나 공격적인 잡음 제거는 하지 않는다. 긴 파일도 반복으로 길이를 채우지 않는다. 여러 문장을 이어 붙인 참조이므로 연속 3분의 한 번의 녹음은 아니다.

로컬 `.env`에서 `HARU_LANGUAGE=ko`와 `HARU_REFERENCE_PATH`를 준비된 파일의 절대 경로로 설정한 뒤 봇을 재시작한다. 비워 두면 기존 언어별 기본 파일을 사용한다.

## 길이와 평가

[Haru 공식 안내](https://github.com/higurashi-ai/Haru/tree/7fe6b7665f8bf035998f401f8cb779fbe53f2751)는 한 화자의 깨끗한 3초~3분 녹음을 요구한다. 3분은 지원 상한이며, 항상 가장 좋은 길이라는 권고는 없다. 길이가 다른 참조는 동일 질문·카드·시드·체크포인트로 비교한다. 테스트는 모델 생성 텍스트와 음량, 프레임 처리 시간, 준비 시간 및 메모리를 기록한다.

생성 텍스트는 출력 음성의 독립적인 음성인식 결과가 아니다. 한글 텍스트와 비무음 출력이 나와도 발음이 좋아졌다는 증거는 아니며, 답변 WAV를 듣고 평가해야 한다. 참조 목소리 변경만으로 입력 이해와 답변 내용의 문제가 해결된다고 보장할 수 없다.

## 이 Mac의 비교 결과 (2026-11-17)

동일한 합성 질문(주말 취미), 현재 Discord 한국어 카드, 시드 0, MLX int8 모델을 사용했다. 길이에 따라 서로 다른 응답이 생성되므로 동일 문장을 읽는 발음 평가가 아니다. 각 참조당 한 번의 실험이다.

| 참조 | 실제 참조 길이 | 첫 프레임 준비 | 이후 프레임 p95 | MLX 최대 메모리 |
| --- | --- | --- | --- | --- |
| yuna | 14.35초 | 0.99초 | 87.5ms | 6.82 GiB |
| kss30 | 29.93초 | 1.42초 | 86.0ms | 6.92 GiB |
| kss176 | 176.00초 | 7.43초 | 86.9ms | 10.43 GiB |

프레임의 실시간 처리 예산은 133.3ms다. 세 경우 모두 비무음 출력과 한글 생성 텍스트가 있었지만, 짧은 KSS 참조는 “네”만 생성했고 긴 참조도 질문과 맞지 않는 답변을 생성했다. 따라서 기능 확인을 발음·대화 품질 개선으로 해석하지 않는다. `artifacts/reference-ab-kss-20261117/summary.json`과 각 하위 폴더의 `reply.wav`를 함께 확인한다.

30초 참조에서 무발화에 가까운 현상이 보고되어, 현재 봇에는 반복 비교 후 단일 원본 문장인 4.66초 KSS 참조를 설정했다:

```dotenv
HARU_LANGUAGE=ko
HARU_REFERENCE_PATH=.runtime/voices/kss/ko-kss-single-37.flac
```

이전 30초·176초 비교 버전은 같은 폴더에 보관한다. 현재 참조는 `raw/train-00037.wav`의 완전한 한 문장이며, 원본 해시·출처·변환 기록은 `ko-kss-single-37.json`에 있다. 서로 다른 문장을 연결하지 않았다. 이전 Yuna 합성 참조로 되돌리려면 `HARU_REFERENCE_PATH=`로 비우고 봇을 재시작한다.

비교를 다시 실행하려면 공통 입력 파일과 매번 새 결과 디렉터리를 지정한다. 아래는 합성 입력 예시이며 실제 마이크 음성을 대표하지 않는다:

```bash
mkdir -p artifacts
say -v Yuna -o artifacts/reference-question.aiff "안녕, 주말에 뭐 하는 걸 좋아해?"
.venv/bin/python scripts/compare_references.py \
  --input artifacts/reference-question.aiff \
  --reference yuna=.runtime/Haru/haru_mlx/haru_mlx/assets/voices/ko.flac \
  --reference kss30=.runtime/voices/kss/ko-kss-30s.flac \
  --reference kss176=.runtime/voices/kss/ko-kss-3min.flac \
  --output-dir artifacts/reference-ab-new
```

30초 버전으로 전환하기 전에, 176초 참조로 로컬 Unix socket·Opus 경로도 확인했다. 입력 870패킷에 예상 출력 131프레임을 모두 받았으며 버린 입력 바이트와 출력 프레임은 0이었다. 결과는 `artifacts/bridge-2026-11-17T10-19-45-732Z/`에 있다. 이 경로 테스트는 기본 카드를 사용해 이름 혼동이 나타났고, 실제 Discord 마이크 연결이나 발음 개선을 검증한 것은 아니다. 이후 새 참조 설정으로 봇을 재시작하여 Discord 온라인 상태를 확인했다.

## 숨소리·무발화 조사 (2026-11-17)

사용자가 30초 참조에서 말 대신 숨소리만 들린다고 보고했다. 당시 마지막 Discord 세션에는 입력 3,668패킷·모델 출력 503프레임·버퍼 넘침 0이 기록됐다. 기존 로그에는 입력 음량, 모델 텍스트량, 재생 버퍼 부족이 없어 실제 입력의 명료성이나 단어 생성 여부를 판단할 수 없었다.

기존 단일 질문 테스트에서도 30초 참조는 “네”만 생성했지만 출력 RMS는 0.0696이었다. 따라서 비무음·한글 존재 검사를 대화 성공으로 간주하면 안 된다.

동일한 세 질문(이름·취미·이름 기억)과 기존 Discord 카드로 세 참조 × 시드 0·1·2를 비교했다. 아래는 각 질문이 시작한 때부터 다음 질문 직전까지 생성한 한글 글자 수다. 질문과 맞는 답변인지, 음성 발음이 명료한지를 평가하는 점수는 아니다.

| 참조 | 시드 0: 질문 1/2/3 | 시드 1: 질문 1/2/3 | 시드 2: 질문 1/2/3 |
| --- | --- | --- | --- |
| Yuna | 45 / 0 / 0 | 39 / 0 / 0 | 44 / 0 / 0 |
| KSS 30초 | 21 / 29 / 23 | 27 / 5 / 7 | 31 / 0 / 0 |
| KSS 원본 한 문장 4.66초 | 32 / 10 / 15 | 50 / 23 / 34 | 31 / 55 / 41 |

결과: `artifacts/breathing-diagnosis-20261117/summary.json`. 4.66초 참조는 세 번 모두 세 구간에서 단어 생성을 이어 갔으나, 이름 혼동·관련 없는 내용·자기소개 반복이 남았다. 한글 수만으로 발음 개선이나 적절한 답변을 보장하지 않는다. 입력은 합성 음성이므로 Discord의 실제 사용자 발화에 대한 효과는 다시 확인해야 한다.

별도로 서술형 친구 카드로 바꾼 시드 0 실험에서는 30초 참조가 감탄사·웃음 정도만 생성했고, 단일 문장 참조도 답변 품질 개선이 확실하지 않았다(`artifacts/breathing-natural-card-20261117/`). 이 카드는 실행 중인 봇에 적용하지 않았다. 발화 시작 강제나 EOP bias 조정도 적용하지 않았다.

운영 진단에는 최근 5초간 입력·출력 RMS/peak, 누적 비공백 생성 문자 수, 재생 FIFO 부족 횟수를 추가했다. 음성·전사 내용을 저장하지 않는다. 출력 프레임·음량이 증가하지만 생성 문자 수가 늘지 않으면 모델이 비언어적 소리만 생성하는 상황과 일치할 수 있다. 입력 RMS가 0이면 입력 전달, 재생 부족이 늘면 출력 전달도 함께 확인한다. 문자 수는 호흡·언어를 구분하는 독립적인 음성인식 결과가 아니다.

새 진단을 포함한 Node 테스트 30개와 구문 검사가 통과했다.

선택한 4.66초 참조도 로컬 Unix socket·Opus 경로에서 입력 870패킷/출력 131프레임, 입력·출력 버림 0으로 통과했다(`artifacts/bridge-2026-11-17T10-41-56-485Z/`, p95 80.8ms). 기본 카드의 합성 질문에 단어가 포함된 응답을 생성했다. 이 검사는 새 진단을 포함한 실 Discord 마이크 대화를 대체하지 않는다. 이후 봇 재시작 및 Discord 온라인 상태를 확인했다.

## 원본 BF16 실행 가능성 (2026-11-17)

실제 하드웨어는 Apple M4, 통합 메모리 32GiB(Mac16,10)다. 로컬 BF16 체크포인트는 10,540,113,510바이트(9.82GiB)이며, MLX `quantize=None`으로 양자화 없이 실행했다. Discord 봇의 모델 프로세스가 없는 대기 상태에서 오프라인으로 측정했고, 실행 중인 봇 설정은 int8로 유지했다.

동일한 50초 입력·4.66초 원본 성우 참조·기존 한국어 카드·시드 0 비교:

| 항목 | MLX int8 | MLX BF16 |
| --- | --- | --- |
| 이후 프레임 p50 | 83.2ms | 125.8ms |
| 이후 프레임 p95 | 86.8ms | 129.1ms |
| MLX 최대 할당량 | 6.56GiB | 10.52GiB |
| 준비 포함 추론 시간 | 32.14초 | 48.05초 |

BF16으로 전체 입력 처리가 완료됐다. MLX 할당량은 운영체제와 다른 앱까지 포함한 전체 RAM 사용량이 아니다. 프레임 예산 133.3ms에 대해 BF16 p95는 여유가 작으며, 이 오프라인 결과로 Discord 실시간 운용이나 긴 세션의 안정성을 보장하지 않는다. 공식 MLX로 원본 가중치를 실행한 것으로, PyTorch 구현과의 비교는 아니다.

BF16 답변에도 참조 문장 내용 재현과 질문과 무관한 내용이 남았다. 한 번의 비교로 품질 차이를 확정하지 않으며, int8 양자화만 해제하면 문제가 해결된다고 볼 근거는 없다. 결과는 `artifacts/bf16-feasibility-20261117/summary.json`에 저장했다.

재현 시 비교 명령에 `--quantize none`을 추가한다. 기본값은 기존과 같이 `--quantize 8`이다.
